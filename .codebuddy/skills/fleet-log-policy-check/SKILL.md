# 车队日志策略业务约束核查

## 用途

以黑盒方式核查题目 09 的 8 条业务规则（规则原文见 `references/business-rules.md`），输出逐条 PASS/FAIL 结论与证据。仅依据接口返回与数据库可见状态判断，不读取实现代码，避免"看代码猜行为"。

## 触发场景

- 完成或修改`internal/fleetlog`业务代码后，需要在提交前做业务回归。
- 需要核对题面规则 1～8 在真实运行的服务上是否成立（审批权限、发布批次、车辆版本、实际生效、停止恢复边界）。
- 需要为验收报告提供可复现的业务证据。

## 输入

| 输入 | 必填 | 说明 |
| --- | --- | --- |
| `--base-url` | 否 | 已运行服务的地址，默认 `http://127.0.0.1:8080`（仅在不使用 `--start` 时生效） |
| `--start` | 否 | 由脚本自行构建并启动网关（临时目录 + 临时 SQLite + 改写端口后的临时配置，教学超时阈值 3 秒），结束后清理 |
| `--port` | 否 | 配合 `--start` 使用的监听端口，默认 18080（避免与本机 8080 上的其他服务冲突，且不改动仓库配置） |
| `--report` | 否 | 输出 JSON 证据文件路径 |

预置凭据（脚本内置）：申请人 `demo-token-applicant`、负责人 `demo-token-approver`、运营 `demo-token-operator`；车辆 `veh-token-01`～`veh-token-05`。

## 执行步骤

1. 运行 `scripts/check_business_rules.py`；带 `--start` 时先 `go build` 网关并用临时 SQLite 启动，避免污染开发库。
2. 脚本按「异常申请 → 审批 → 试点 → 回执 → 超时 → 停止 → 恢复 → 正常推广」顺序推进真实流程，逐步断言规则。
3. 任一步骤失败时，脚本继续执行剩余可执行项，最后统一汇总，避免首个失败掩盖后续缺陷。
4. 阅读脚本输出表格，定位失败项对应的规则编号与接口证据；需要细节时查看 `--report` 生成的 JSON。

```bash
python .codebuddy/skills/fleet-log-policy-check/scripts/check_business_rules.py --start --report business-check.json
```

## 输出格式

```text
[规则2] 同车队第二个申请不得生成活动  PASS  (HTTP 409 conflict)
[规则5] 跨车回执拒绝并留痕            PASS  (HTTP 403 forbidden 留痕=['cross_vehicle', ...])
[规则6] 失败回执不改变此前生效值      FAIL  (applied=45 状态=失败，期望 applied=60)
------------------------------------------------------------------------
合计 49 项：PASS 48 / FAIL 1
退出码：1
```

失败项需同时给出口径（规则编号 + 期望值 + 实际值 + 请求证据）。

## 失败处理

- 连接失败：提示先启动网关（`make run-gateway` 或 `go run ./cmd/gateway`），或改用 `--start`。
- 端口占用：`--start` 会直接报错并给出现有进程提示，不要静默改端口掩盖问题。
- 单条断言失败：保留该条为 FAIL，禁止跳过后判定整体通过；修复后重跑脚本，用同一命令复检。
- 预置数据被污染（库中已有活动）：脚本 `--start` 使用临时库规避；对已有服务运行时，若断言因历史数据失败，需在报告中标注"环境不洁"并改用临时库复跑。

## 完成标准

1. 脚本退出码为 0，且输出中 FAIL 数为 0（当前版本共 49 条断言）。
2. 覆盖规则 1、2、3、4、5、6、7、8 各至少一条断言，且包含时序相关断言（60 秒超时与超时后迟到成功）。
3. 报告文件保存到 `docs/evidence/` 或在验收报告中引用其路径与时间。
