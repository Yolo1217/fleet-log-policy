# 题目 09 需求分析 — 测试车队日志策略的申请、审批、分批发布与结果核查

> 依据：《Go 项目业务场景题》题目 09 题面 + 第一部分共同要求。本文档是开发、测试、验收三个 Agent 的共同输入。

## 1. 业务概述

车云研发团队排查问题需要临时调高某车队 5 台测试车辆的非安全诊断日志上报频率。流程为：研发提出配置申请 → 负责人审批 → 运营先向 2 台试点车发布 → 试点结果明确后推广至剩余 3 台 → 车端拉取配置并回执 → 负责人复核后可结束活动；异常时负责人可停止活动，对已生效车辆发起恢复（下发各车活动前设置）。

核心业务事实：**"已下发" ≠ "已生效"**。系统必须对每台车分别保存期望值（最新已发布版本的目标间隔）与已生效值（车端回执确认的实际间隔），任何时点都能解释每台车的发布前值、期望值、生效值、成功/失败/未确认状态。

## 2. 角色与预置数据

| 角色 | 能力 | 不能做 |
| --- | --- | --- |
| 研发申请人 | 创建申请（原因 + 5 台车辆 + 新间隔）、退回后修改再提交、查看本人申请 | 审批本人申请；批准后原地改参数 |
| 审批负责人 | 批准/退回申请；复核试点与整体结果；决定停止活动；批准恢复；活动记为完成 | 审批自己提出的申请（申请人不能是审批人） |
| 发布运营 | 选 2 台试点车执行试点发布、确认推广剩余 3 台、停止未发送部分、发起恢复 | 绕过试点检查直接推广；代替负责人决定停止 |
| 模拟车辆 | 持车辆凭证认证 → 拉取面向自己的最新已发布版本 → 按版本回执成功/失败 | 取得非本车配置；伪造他车回执 |

预置：1 个车队、5 台测试车（1 台在线试点、1 台离线试点、3 台推广车）、上述角色账号。配置项仅"日志上报间隔"，10～300 秒，初始均 60 秒（各车活动前值）。金额、货币不涉及。

## 3. 状态机设计

### 3.1 申请（Application）

```text
待审批 ──批准──▶ 已批准（生成发布活动）
   │
   └──退回──▶ 已退回 ──修改再提交──▶ 待审批（保留历史版本）
```

- 申请内容：排查原因、5 台目标车辆（固定车队）、新间隔（10～300 整数秒）。
- 约束：审批人 ≠ 申请人；已批准申请参数不可原地修改（如需变更只能撤回重提，本题不要求）。

### 3.2 发布活动（Campaign）

```text
已批准（未发布）
  ──运营发起试点(2台)──▶ 试点中
试点中 ──两台均回执成功──▶ 试点成功 ──运营确认推广(3台)──▶ 推广中
试点中 ──任一试点车失败或超时──▶ 已暂停 ──负责人决定──▶ 已停止
推广中 ──5 台全部确认成功──▶ 待结案 ──负责人记为完成──▶ 已完成
推广中 ──异常时负责人决定停止──▶ 已停止
已停止 ──负责人批准恢复──▶ 恢复中 ──需恢复车辆全部确认──▶ 已恢复
```

- 同一车队同时只允许一个未结束活动（待发布/试点中/推广中/恢复中均为"未结束"）。
- 试点阶段其余 3 台不得获得该活动配置。
- 已停止仅阻止未发送部分继续下发；已下发与已生效记录保留。
- 停止活动**不等于**撤销车端配置；恢复是新一轮可核查的下发。

### 3.3 每车发布版本（VehicleRelease）

每车独立版本号递增。一次活动对每台车最多产生两个发布版本：活动版本、恢复版本。

```text
待下发 ──运营下发──▶ 已下发待回执 ──回执成功──▶ 已生效
                        │
                        ├──回执失败──▶ 失败（生效值不变，保留原因）
                        └──60 秒无有效回执──▶ 超时（保留历史；当前期望版本迟到成功可更新该车结果）
```

- 车辆只能拉取**面向自己的最新已发布版本**（期望值）。
- 生效值变更仅由合法回执驱动；失败不改变此前生效值。
- 恢复版本目标 = 该车活动前设置（预置 60 秒，或该车在活动前的实际生效值）。

## 4. 业务规则逐条落点（题面规则 → 系统约束）

| # | 题面规则 | 系统约束 |
| --- | --- | --- |
| 1 | 申请含原因、5 台车、新间隔；审批人非申请人；退回可改再提交；批准后参数不可改 | 申请表单服务端校验 + 角色校验 + 不可变约束 |
| 2 | 同车队同时一个未结束活动；试点 2 台，其余不提前获得配置 | 活动唯一性约束（DB 唯一/状态检查）；试点期车辆拉取接口仅返回被选车辆版本 |
| 3 | 两台试点均成功才可推广；失败/超时暂停；负责人可停止；不得绕过检查 | 推广接口前置校验试点状态，非法推广拒绝并记录 |
| 4 | 车辆只取得面向自己的最新已发布版本；每车版本递增；期望值与生效值分别保存 | 车端拉取接口按车辆凭证过滤；版本单调递增；expected/applied 分字段 |
| 5 | 回执须鉴权且对应本车已发布版本；重复成功不重复记账；旧版本不能覆盖新版本；未知版本、跨车回执拒绝并记录 | 回执接口鉴权 + (车辆, 版本) 匹配 + 幂等去重 + 版本单调性检查，异常入异常记录表 |
| 6 | 60 秒无回执显示超时；当前期望版本迟到成功可更新结果并保留超时历史；失败不改生效值；已停止活动不因迟到回执重启 | 教学时钟超时扫描；迟到成功仅更新该车结果；活动终态不因回执变更 |
| 7 | 停止仅阻止未发布部分；不抹掉已发/生效记录；负责人批准恢复；为曾发布过配置的车辆建恢复版本，目标为活动前设置 | 停止保留已发/未发范围字段；恢复需负责人批准；恢复范围 = 期望版本已下发的车辆 |
| 8 | 全部目标车确认成功后负责人可记完成；停止保留已发未发范围；恢复完成须全部需恢复车确认；逐车核查发布前值/期望值/生效值/成败/未确认；有未确认项不得显示"全部恢复" | 结案/恢复完成接口前置校验；核查页面按车列出五类信息 |

## 5. 边界与异常清单（必须可操作且有持久化结果）

1. 申请人 = 审批人 → 拒绝审批。
2. 间隔越界（<10 或 >300 或非整数）→ 申请校验失败。
3. 同车队已存在未结束活动时再次发起 → 拒绝。
4. 试点未完成（含失败/超时暂停）时尝试推广 → 拒绝并留痕。
5. 非试点车在试点阶段拉取配置 → 拿不到活动版本（返回其当前生效版本）。
6. 重复回执（同车同版本多次成功）→ 幂等，只记一次生效。
7. 旧版本回执晚到 → 不覆盖新版本生效值，留审计。
8. 未知版本回执 / 跨车回执（车 B 回执车 A 的版本）→ 拒绝并记录。
9. 未鉴权或无效凭证回执/拉取 → 拒绝。
10. 超时后迟到成功（当前期望版本）→ 更新该车结果，保留超时历史。
11. 活动已停止后迟到成功 → 只更新车辆结果，不重启活动。
12. 推广前试点车中含离线车 → 60 秒超时 → 暂停。
13. 停止后已生效车辆仍在用新间隔 → 状态如实展示，直到恢复完成才回到活动前值。
14. 越权：非负责人审批/停止/结案，非运营发布，申请人越权改已批准申请 → 均拒绝。
15. 服务重启 → 所有申请、活动、版本、回执、异常记录可查询（持久化）。

## 6. 必须演示的五个完整场景

| 场景 | 主线 | 关键验证点 |
| --- | --- | --- |
| 正常推广 | 申请 → 审批 → 2 台试点成功 → 推广 3 台 → 逐车核查 → 结束 | 逐车生效值=期望值；版本递增 |
| 审批与试点分支 | 申请退回修改再批准；试点一车失败/超时 → 暂停 → 负责人停止 | 未试点车未收到配置；停止保留已发/未发范围 |
| 恢复分支 | 部分车已生效 → 停止 → 批准恢复 → 下发更高版本（60 秒） | 区分已恢复与未确认；未确认不得显示"全部恢复" |
| 网络分支 | 离线车晚拉取、旧回执晚到、超时后成功、重复回执、跨车身份 | 生效状态不被混淆；异常均留痕 |
| 结果核查 | 同活动含成功、失败、未确认车辆 | 不能只展示活动总状态 |

## 7. 技术要点

- 架构：沿用脚手架分层（gateway HTTP → 业务 service → repo → 数据库）；单服务单库即可，不强制微服务拆分。
- 数据库：本地 MySQL 主库 `questions`（`configs/config.yaml` 的 `database.dsn`，默认 `root:root@tcp(127.0.0.1:3306)/questions?charset=utf8mb4&parseTime=True&loc=Local`），启动自动迁移建表；单元测试与隔离核查改用 SQLite（`FLEETLOG_DB_PATH`）避免污染主库，两套后端共用同一 Gorm 模型与迁移，业务规则一致。
- 教学时钟：60 秒超时可配置缩短用于演示，须在文档与页面注明；测试与演示同规则。
- 页面（简单 HTML 即可）：申请与审批页、试点与推广操作页、逐车进度核查页、恢复结果页。
- 模拟车辆：提供车辆拉取与回执接口 + 演示脚本/页面，可触发成功、失败、超时、重复、跨车回执。

## 9. 可验证的验收条件（验收 Agent 逐项对照）

1. 全部 15 条边界异常项均有接口级拒绝/处理结果且持久化可查。
2. 五个演示场景可实际操作走通，不能用写死数据代替。
3. 每车任意时刻可查：发布前值、当前期望值（版本号+间隔）、已生效值（版本号+间隔）、状态（待下发/已下发/成功/失败/超时/未确认）。
4. 试点期推广被拒、非试点车拿不到配置、跨车/未知/旧版本回执被拒均有留痕。
5. 审批人≠申请人、角色越权全部拒绝。
6. 服务重启后数据完整；DB 中每车版本单调递增无回退。
7. 核心业务包单元覆盖率 ≥85%，`go vet`、`go test -race` 通过。
8. `main` 分支无直接提交；合并经 PR 且门禁通过；部署对应主分支发布提交。
